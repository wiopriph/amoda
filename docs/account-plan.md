# Личный кабинет Amoda — план

Дата: 2026-09-02. Статус: черновик на согласование.

## 1. Что есть сейчас (аудит)

**Авторизация**
- `@nuxtjs/supabase`, e-mail + пароль и magic link (`app/pages/auth.vue`, `app/composables/useAuth.ts`).
- Роль admin — `app_metadata.roles` в Supabase Auth; проверка на клиенте (`middleware/admin.ts`) и сервере (`server/utils/assertAdmin.ts`).
- В Supabase Auth включён только провайдер `email`. Phone-провайдер выключен, SMS-провайдер не настроен.
- В публичном UI нет ни одной ссылки на `/auth` — туда попадает только админ через редирект.
- Пользователей в Auth: 1 (админ).

**База (Supabase)**
- Уже есть, но не используется: `profiles (user_id, name, phone, role)` — пусто, автосоздания нет; `orders.user_id`, `carts.user_id` — всегда NULL; `orders.cart_id` — не заполняется; `reviews`, `order_events` — пусто.
- Нет таблиц купонов и избранного.
- Корзины: 17 614 (все DRAFT), до чекаута дошло 6, строк `cart_items` 60. Таблица `orders` пуста.
  Вывод: реальные заказы идут через WhatsApp по коду корзины, сайтовый чекаут почти не работает как канал.

**Корзина / чекаут / заказ**
- Корзина серверная, привязана к cookie `sid` (180 дней), код корзины `public_code` уходит в текст WhatsApp.
- Чекаут: имя + телефон, без логина; контакт кладётся в `carts.contact_snapshot`, заказ — в `orders.guest_contact`.
- Страница `/order/[number]` открыта всем, кто знает номер (формат `YYMMDD-NNNNN`, перебираем). Показывает имя и телефон.
- Статусы заказа: PLACED / CONFIRMED / DELIVERED / CANCELLED; оплата: UNPAID / PAID / REFUND_*.

**Избранное**
- Только `localStorage` (`useFavorites.ts`), теряется при смене устройства/браузера.

**Админка**
- Отдельный layout `admin`, страницы под `/admin/**`, свой `Sair`. Прятать особо нечего — нужно лишь, чтобы обычный пользователь после логина не видел ничего админского и попадал в кабинет.

## 2. Целевая картина

Принципы: минимум экранов, один layout, ничего лишнего. Копирайт в tu-регистре, как на сайте.

**Идентичность.** Основной идентификатор клиента — телефон (Ангола = WhatsApp). Сейчас вход по e-mail, но кабинет и профиль строятся вокруг `profiles.phone`, чтобы при подключении OTP ничего не переделывать.

**Страницы кабинета (`/conta`)**
| Маршрут | Содержимое |
|---|---|
| `/conta` | Приветствие, имя/телефон, последняя reserva со статусом, быстрые ссылки. Для админа — ссылка «Admin». |
| `/conta/reservas` | Список заказов: номер, дата, статус, сумма. Карточка → детальная. |
| `/conta/reservas/[number]` | Детали заказа (переиспользуем блоки из `/order/[number]`). |
| `/favorites` | Остаётся по старому URL, но синхронизируется с сервером для залогиненных. |
| `/conta/cupoes` | Мои купоны: код, условие, срок, «использован». |
| `/conta/dados` | Имя, телефон, e-mail; выход. |

Layout `account`: обычные header/footer сайта + компактная навигация кабинета (горизонтальные пилюли на мобиле, слева на десктопе).

**Вход.** Иконка «пользователь» в хедере: залогинен → `/conta`, нет → `/auth`. После логина редирект в `/conta` (или `redirected_from`).

**Стимулы регистрироваться и заказывать через сайт**
1. Welcome-купон после регистрации (например, скидка на первый заказ через сайт) — виден в кабинете и подставляется в чекаут.
2. Статус заказа в кабинете (Novo → Confirmado → Pronto → …) вместо «спросить в WhatsApp».
3. Чекаут в один тап: имя и телефон уже заполнены из профиля.
4. Избранное не теряется между устройствами.
5. После гостевого заказа — мягкое предложение «cria conta para acompanhar a reserva» (с OTP это будет один шаг, телефон уже введён).

## 3. Решения (2026-09-03)

- Терминология: **Pedidos** («Os meus pedidos»). Публичная страница после чекаута пока остаётся «Reserva».
- Вход: форма `/auth` остаётся как есть (пароль + magic link), админ логинится там же. Замена формы — только вместе с OTP по телефону.
- Скрытый релиз: фича-флаг `NUXT_PUBLIC_ACCOUNT_ENABLED` (runtimeConfig.public.accountEnabled). Флаг выключен → `/conta/**` даёт 404 всем, кроме админа; иконка аккаунта в хедере видна только админу. Флаг включён → кабинет открыт всем.
- `orders` пуста намеренно (чистили), 99% заказов идёт через WhatsApp. `/order/[number]` не закрываем.
- Купоны и отзывы — отдельными поздними этапами.
- Телефон: источник правды — подтверждённый `auth.users.phone` (после OTP), `profiles.phone` только зеркало через триггер. В кабинете номер не редактируется, смена — через поддержку в WhatsApp. В чекауте используется номер, под которым вошли. Своей уникальности на `profiles.phone` нет, её держит Supabase Auth.
- Структура кабинета: три вкладки — Pedidos (`/conta`), Favoritos (`/favorites`, для залогиненных в layout кабинета), Os meus dados (`/conta/dados`). На мобиле сегмент-контрол с иконками, на десктопе колонка слева.
- Вход по e-mail временный, чтобы не ломать админку. С приходом OTP: клиенты входят по номеру на своей странице, админ — по e-mail на отдельном скрытом маршруте (`/admin/login`). Выносить админку в отдельное приложение не планируем.
- Рекомендация по купонам на будущее: процентная скидка (5–10%) «только на заказ через сайт», одноразовая на пользователя, вводится в чекауте, серверная валидация, скидка видна в заказе/админке/Telegram.

## 4. Этапы

### Этап 1 — фундамент за флагом
- `migrations/2026-09-03_account_profiles.sql`: триггеры `auth.users → profiles` (создание и зеркало телефона), `created_at/updated_at`, RLS, бэкфилл существующих пользователей.
- Флаг `accountEnabled`, middleware `account` (404 без флага для не-админа, редирект на `/auth` без сессии).
- Layout `account`: обычные header/footer + навигация кабинета.
- Страницы `/conta` (Pedidos, пока пустое состояние) и `/conta/dados` (имя, номер только для чтения, e-mail, выход).
- API `GET/PATCH /api/account/profile` (PATCH меняет только имя).
- Хедер: иконка аккаунта (по флагу / для админа). `/auth`: после входа редирект в `/conta` (админ без флага → `/admin`), залогиненному — кнопка «A minha conta».
- Sitemap: исключить `/conta/**`.

### Этап 2 — заказы в кабинете (сделано 2026-09-03)
- `place-order` пишет `user_id` (если вошла) и `cart_id` (корзина по cookie `sid`).
- Плагин `account-link.client.ts` после входа вызывает `POST /api/account/link-session`: корзины этого `sid` получают `user_id`, а их заказы без владельца — тоже. Один раз на пользователя за вкладку.
- API `GET /api/account/orders` (список, до 50, с превью фото) и `GET /api/account/orders/[number]` (чужой заказ = 404). Общий фетч заказа вынесен в `server/utils/orders.ts`, публичный `/api/orders/get` использует его же.
- Страницы `/conta` (список) и `/conta/pedidos/[number]` (детали, статус с пояснением, кнопка WhatsApp по номеру заказа). Тексты статусов для клиентки — `shared/constants/orderStatus.ts`.

### Этап 3 — избранное на сервере (сделано 2026-09-03)
- `migrations/2026-09-03_favorites.sql`: таблица `favorites (user_id, product_id, created_at)`, RLS без политик.
- API `GET/POST /api/account/favorites`, `DELETE /api/account/favorites/[id]`, `POST /api/account/favorites/merge`. Список в формате карточки каталога (цена и фото default-варианта), снятые с продажи товары скрыты, но не удалены.
- `useFavorites`: гость — localStorage, вошедшая клиентка — сервер с оптимистичным обновлением и откатом. При входе локальный список сливается на сервер и очищается. Инициализация и реакция на вход/выход вынесены в плагин `favorites.client.ts`.

### Этап 4 — чекаут (сделано 2026-09-03)
- Чекаут: для вошедшей клиентки имя и номер подставляются из профиля (номер пока редактируемый; с OTP станет подтверждённым и его можно будет не спрашивать).
- `/api/orders/get` отдаёт `isMine` (заказ принадлежит текущей сессии). На `/order/[number]` владелица видит кнопку «Ver na minha conta», гость при включённом флаге — мягкий блок «Criar conta» со ссылкой на вход и возвратом в `/conta`.

### Этап 5 — вход по SMS-коду (код готов 2026-09-03, ждёт настройки Supabase и провайдера)
Решение по провайдеру: только SMS, без WhatsApp. Сначала Infobip (оплата в USD, тест доставки на Unitel и Africell), потом eSMS Africa (оплата в AOA, прямые маршруты) — оба через Send SMS Hook, замена провайдера = замена ключей. Twilio отвергнут: $0.31 за SMS в Анголу.

Что сделано в коде:
- `/entrar`: «номер → код», регистрация и вход — одно действие (`signInWithOtp({ phone })` + `verifyOtp`). Повторная отправка через 60 с, автосабмит при 6 цифрах, ошибки Supabase переведены (`humanizeAuthError`). Опциональная капча Cloudflare Turnstile по `NUXT_PUBLIC_TURNSTILE_SITE_KEY`.
- `/admin/login`: e-mail + пароль только для админа, ссылок на него нет. Старый `/auth` удалён.
- `POST /api/auth/send-sms`: Send SMS Hook. Проверка подписи Standard Webhooks (`server/utils/standardWebhooks.ts`), адаптеры провайдеров в `server/utils/sms.ts` (`infobip`, `log` для разработки).
- `migrations/2026-09-03_account_claim_orders.sql`: функция `claim_orders_by_phone` — гостевые заказы с тем же номером получают владельца при входе (вызов из `link-session`).
- Чекаут: у вошедшей клиентки номер подставлен из аккаунта и не редактируется.

Переменные окружения (`.env`):
```
SUPABASE_SMS_HOOK_SECRET=v1,whsec_...   # Authentication → Hooks → Send SMS → Generate secret
SMS_PROVIDER=infobip                     # или log
SMS_SENDER_ID=Amoda
INFOBIP_BASE_URL=xxxxx.api.infobip.com
INFOBIP_API_KEY=...
NUXT_PUBLIC_TURNSTILE_SITE_KEY=          # опционально
```

Чек-лист настройки Supabase (Authentication):
1. Providers → Phone: Enable phone provider. SMS provider там можно оставить любой — его перекрывает хук.
2. Hooks → Send SMS Hook: HTTP, URL `https://amoda.ao/api/auth/send-sms`, сгенерировать секрет → в `SUPABASE_SMS_HOOK_SECRET` на хостинге.
3. Providers → Phone → Test OTPs: добавить тестовые номера с фиксированным кодом для разработки (SMS не отправляется).
4. Rate limits: SMS в час — небольшое число (например 30), OTP expiry 5–10 минут, длина 6.
5. Опционально: Attack protection → CAPTCHA (Turnstile) и ключи в env.

Чек-лист открытия:
- Применить миграции `profiles`, `favorites`, `claim_orders`.
- Проверить доставку на реальных номерах Unitel и Africell, засечь задержку.
- `NUXT_PUBLIC_ACCOUNT_ENABLED=true` на хостинге.
- Первые дни следить за расходом SMS и лимитами.
